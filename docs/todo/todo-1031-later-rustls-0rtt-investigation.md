# TODO-1031: Rustls-standard 0-RTT transport path

## Why

TODO-720 correctly disabled a half-wired 0-RTT claim. TODO-1030 settled the standard-crypto posture. This task implements only rustls-standard 0-RTT and never reopens first-party or private AEADs.

## Scope Update (2026-09-23)

The original task was investigation-only. The user subsequently directed implementation and continuation through the planned task series. This explicit scope update supersedes the investigation-only restriction. The implementation is opt-in and permits only a complete client-initiated bidirectional stream message explicitly marked replay-safe. The VPN product does not send H3 control/QPACK streams, MASQUE CONNECT, tunnel-stream fallback, DATAGRAM, or TUN payload in 0-RTT. H3 initialization stays after TLS completion because construction immediately emits its SETTINGS prologue. A server returns HTTP 425 for any early H3 request before invoking request callbacks or MASQUE/TUN handling, and drains any rejected body.

## Protocol Decision

- Use only directional rustls `PacketKey` and header-protection objects from `ConnectionCommon::zero_rtt_keys()`.
- Reject private-AEAD 0-RTT. Private packet protection remains limited to its authenticated 1-RTT boundary.
- Enable server early data only when a shared anti-replay register is attached. Use shared stateful session storage and disable the stateless ticketer on that path; rustls consumes stateful TLS 1.3 tickets with `take()`.
- Keep unmarked streams and DATAGRAM frames out of the client 0-RTT sender. Reject 0-RTT unidirectional and server-initiated stream IDs, and retain a per-connection early-data byte cap.
- Reject received early H3 requests with HTTP 425 before application callbacks or MASQUE/TUN side effects, and drain any request body.
- On absent ticket or server rejection, leave data buffered or requeue in-flight streams for 1-RTT. A replay-register drop does not commit the packet number or generate an ACK.
