# TODO-1066: Freeze one pre-ring QFENC1 ciphertext and open it with ring

## Why

Before `bbc93fe2`, `legacy_envelope_is_authenticated_and_upgraded_without_plaintext_leakage` sealed with first-party `ChaCha20Poly1305` and opened with ring. After that commit both sides are `RingChaCha20Poly1305`. The test still proves the current code roundtrips. It no longer proves a file written by the deleted sealer still opens. If the old nonce or counter layout differed from ring, existing `QFENC1` registries break and no test notices.

## Current code

- Magic `QFENC1` (`LEGACY_MAGIC`) in `src/implementations/server/qkey_registry_storage.rs`.
- Layout: magic, 12-byte nonce, ciphertext including the 16-byte tag.
- `decode_legacy` calls `decrypt`, which uses `RingChaCha20Poly1305::open_with_u64_counter(0, ...)`.
- The live test seals with `RingChaCha20Poly1305` at counter 0 and the same nonce layout. Plaintext and nonce are generated inside the test. Nothing is checked in as bytes from the old sealer.
- The first-party module is gone, so the old ciphertext cannot be regenerated from current source.

## Target

- One checked-in golden blob: the exact bytes a run of the pre-deletion sealer produced for a documented key, nonce, AAD, and plaintext.
- The current `decode_legacy` / `decrypt` path opens that blob and returns that plaintext.
- The golden file lives next to the test (or as a byte array in the test) and is not produced by `RingChaCha20Poly1305` in the test process.
- The existing roundtrip test stays. It is a different claim.

## Non-goals

- Do not restore `chacha.rs` or `poly1305.rs`.
- Do not change the on-disk layout.
- No frontend change.

## Design

1. From commit `a87b9584` (parent of the deletion, still has `ChaCha20Poly1305`), run only the sealer that the old test used: key, nonce, counter 0, empty or header AAD, as that test did. Capture magic || nonce || ciphertext.
2. Record in this file: commit, key hex, nonce hex, AAD, plaintext, ciphertext hex. The command is a throwaway `cargo test` or a one-file example on that commit. Do not commit the old module.
3. Add those bytes to the current test. Open through `RegistryStorage`'s legacy path, or through `decrypt` if the test cannot stand up a full registry. Assert plaintext equality and that the rewrite reason is the legacy upgrade.
4. If step 1 shows the old ciphertext differs from ring's seal of the same inputs, that is a migration bug. Fix `decrypt` so the golden opens. Do not "fix" the test by resealing with ring.

## Sub-Tasks

- [ ] Generate the golden on `a87b9584` and paste the hex into Notes before writing the test.
- [ ] Test opens the golden and checks the plaintext.
- [ ] Confirm the golden ciphertext is not equal to a comment that says "generated by ring".
- [ ] `cargo test --offline --test` or the inline qkey test name that carries the golden passes.

## Acceptance

- The test source contains a fixed `&[u8]` (or fixture file) that does not call `seal` to build itself.
- Opening it yields the documented plaintext.
- A one-byte flip of the golden fails authentication.
- `chacha.rs` stays deleted.

## Risks

- The old test's AAD might be `&[]` or the header. Copy the actual `seal_with_u64_counter` arguments from `a87b9584:src/implementations/server/qkey_registry_storage.rs`. A wrong AAD makes a correct ring fail and invites a fake fix.
- Building the whole old tree may be heavy. A tiny example that links only the old `qf-crypto` sealer is enough. Disk check before that build.
