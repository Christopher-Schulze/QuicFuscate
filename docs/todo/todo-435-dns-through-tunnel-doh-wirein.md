# TODO-435: DNS through tunnel (DoH wire-in, DNS proxy, server forwarding)

## Goal
Implement full DNS-through-tunnel: a client-side DNS proxy that intercepts port 53 traffic, resolves via DoH through the encrypted QUIC tunnel, and a server-side DNS forwarding service that receives DoH queries from clients and forwards them to configured upstream resolvers. This eliminates DNS leaks, ensures all DNS traffic is encrypted and tunneled, and makes DNS look indistinguishable from normal HTTPS traffic to DPI.

## Implemented State

- `src/dns/mod.rs` now contains the shared DNS primitives: RFC 1035 query parsing, response/NXDOMAIN building, DoH request handling with a cached `reqwest::Client`, and server-side upstream UDP forwarding with response-source validation.
- `src/implementations/server/mod.rs` wires DNS into the live server MASQUE/TUN path. MASQUE uplink payloads that are raw IPv4 or IPv6 UDP/53 DNS queries are intercepted before they are written to the server TUN interface, so DNS does not leak into generic OS forwarding.
- Intercepted DNS queries are resolved through `ServerConfig.dns_servers` using `crate::dns::forward_dns_query`; upstream failures fall back across configured resolvers and then to NXDOMAIN for parseable queries.
- DNS responses are rebuilt as raw IPv4 or IPv6 UDP packets with swapped tuple, preserved client source port, valid IP/UDP checksums, and OS-fingerprint TTL/hop-limit normalization, then queued into the connection MASQUE downlink queue.
- The downlink queue is drained from both the per-datagram path and housekeeping, so async DNS responses generated by `spawn_blocking` are returned even if no further client datagram arrives.
- Tests cover IPv4 and IPv6 UDP/53 parsing and response packet rebuilding.
- `scripts/tests/tun-e2e-dns-leak-netns.sh` provides the real Linux network-namespace E2E proof: server/client TUN over MASQUE, a DNS query to the server TUN IP, and tcpdump on the client underlay asserting zero raw TCP/UDP port 53 packets.

## Problem Analysis

### DNS leaks
Without a DNS proxy, client applications resolve DNS directly via the system resolver, which typically uses the ISP's DNS servers. This leaks the domains being visited to the ISP and any network observer, completely undermining the VPN's purpose. Even if all IP traffic goes through the tunnel, DNS queries bypass it.

### DPI detection
DNS queries on port 53 are plaintext (UDP). DPI can trivially see which domains a user is resolving. Even DNS-over-TLS (port 853) is a distinct protocol that DPI can identify and block. DoH (port 443, HTTPS) is the only DNS protocol that blends in with normal web traffic.

### Current DoH limitations
1. **JSON API only**: `resolve_doh_single()` uses Google's JSON DoH API (`?name=domain&type=A`). This is non-standard — the RFC 8484 wire format sends raw DNS packets in HTTP POST body or base64url in GET parameter. The JSON API is Google-specific and not supported by all DoH providers.
2. **A records only**: Only type A (IPv4) is resolved. No AAAA (IPv6), no MX, no TXT, no SRV, no PTR.
3. **No caching**: Every resolution is a fresh HTTP request. No TTL-based cache.
4. **Not a proxy**: It's a library function, not a system-level DNS proxy that intercepts port 53.

### Server-side gap
The server receives client traffic via TUN and NATs it to the internet. But DNS queries from the client go to whatever DNS server the client's system is configured to use — which may be outside the tunnel. The server has `dns_servers` config but does nothing with it except pass it to the client as metadata.

### Key design decisions
1. **Wire format (RFC 8484)**: Replace JSON API with RFC 8484 wire format. DNS query is a raw DNS packet sent as HTTP POST body with `Content-Type: application/dns-message`, or base64url in GET `?dns=` parameter. This is the standard, supported by Cloudflare, Google, Quad9, and all major DoH providers.
2. **Server-side DoH endpoint**: The server exposes an HTTP/3 endpoint at `/dns-query` that accepts DoH wire-format queries. This is the same path used by the QUIC tunnel — the DNS query is just another HTTP/3 request through the tunnel, indistinguishable from VPN data traffic.
3. **Client DNS proxy**: A local UDP listener on `127.0.0.1:5353` that receives redirected port 53 traffic, parses DNS wire format, and forwards via DoH through the tunnel.
4. **Split DNS**: Domain-based routing — configured domains (e.g., `*.corp.example.com`) are resolved locally, everything else goes through the tunnel.
5. **DNSSEC validation**: Optional, performed server-side before returning the response to the client.

## Implementation Plan

### Phase 1: RFC 8484 wire-format DoH client
1. Create `src/dns/mod.rs` with DNS wire-format parser/serializer (RFC 1035 header + questions + answers).
2. Implement `resolve_doh_wire()` that sends a raw DNS packet as HTTP POST to `/dns-query` with `Content-Type: application/dns-message`, `Accept: application/dns-message`.
3. Replace `resolve_doh_single()` JSON parsing with wire-format parsing. Keep `resolve_doh()` as the public API but route through wire format.
4. Support all DNS record types: A, AAAA, CNAME, MX, NS, SOA, TXT, SRV, PTR, CAA.
5. Parse TTL from response for caching.

### Phase 2: Client-side DNS proxy
1. Create `src/dns/proxy.rs` with `DnsProxy` struct that binds a UDP socket on `127.0.0.1:5353`.
2. Install iptables/nftables REDIRECT rule: `iptables -t nat -A OUTPUT -p udp --dport 53 -j REDIRECT --to-ports 5353` (and same for TCP).
3. On receiving a DNS query: parse wire format, check cache, forward via DoH through the tunnel, cache response by TTL, return to client.
4. Handle both UDP and TCP DNS queries (TCP for large responses, zone transfers).
5. Support EDNS0 (OPT record) for larger UDP responses and DNSSEC OK (DO) bit.

### Phase 3: DNS cache
1. Create `src/dns/cache.rs` with `DnsCache` — TTL-aware cache keyed by `(domain, record_type)`.
2. Use `moka` crate (already a potential dep) or a simple `DashMap` with periodic TTL eviction.
3. Cache hits return immediately without network round-trip.
4. Negative caching: cache NXDOMAIN responses for their TTL (minimum 5s per RFC 2308).
5. Cache size limit with LRU eviction (default 10,000 entries).

### Phase 4: Server-side DoH forwarding
1. Create `src/implementations/server/dns_forwarder.rs` with `DnsForwarder` struct.
2. Register HTTP/3 route `/dns-query` on the server's HTTP/3 handler.
3. On receiving a DoH wire-format query: parse, validate, forward to configured upstream resolvers via standard UDP DNS (port 53).
4. Forward to primary upstream first, fall back to secondary on timeout (1s).
5. Return the upstream response as DoH wire-format HTTP response.
6. Server-side cache: shared across all clients, TTL-aware.

### Phase 5: Split DNS support
1. Add `split_dns` config to `ServerConfig` and client config: `Vec<SplitDnsZone>` where each zone has a domain pattern and a resolver address.
2. Client DNS proxy checks incoming query domain against split DNS zones before deciding to tunnel or resolve locally.
3. Local resolution uses the system resolver (via `std::net::ToSocketAddrs` or a direct UDP query to the configured local resolver).
4. Wildcard support: `*.corp.example.com` matches `api.corp.example.com` but not `corp.example.com` (unless explicitly listed).

### Phase 6: DNSSEC validation (server-side)
1. When DNSSEC is enabled (config flag), the server sets the DO (DNSSEC OK) bit in upstream queries.
2. Validate RRSIG records on responses using the trust anchor (root KSK).
3. Use `trust-dns-resolver` or a lightweight DNSSEC validator.
4. If validation fails, return SERVFAIL to the client.
5. This is optional and off by default (performance impact: adds ~1 RTT for DNSKEY chain validation on first query per zone).

### Phase 7: search_domains support
1. Add `search_domains: Vec<String>` to client config (e.g., `["corp.example.com", "internal"]`).
2. DNS proxy appends search domains to bare names (e.g., `api` → `api.corp.example.com`) before resolution.
3. Follow RFC 6761: search domains are NOT applied to fully-qualified domain names (ending with `.`).

## Technology Choices

### Chosen: RFC 8484 wire format (HTTP POST with `application/dns-message`)
- **Standard**: Supported by all major DoH providers (Cloudflare, Google, Quad9, NextDNS).
- **Efficient**: Binary format, no JSON parsing overhead. A typical DNS query is ~30 bytes.
- **Complete**: Supports all record types, EDNS0, DNSSEC. JSON API only supports A/AAAA in Google's implementation.
- **Stealth**: The HTTP request looks like any other POST to an API endpoint. No `?name=domain&type=A` query string that could be fingerprinted.

### Chosen: `hickory-dns` (formerly `trust-dns`) for DNS wire-format parsing
- Pure Rust, async, supports DNSSEC, widely used.
- `hickory-proto` crate provides wire-format parsing/serialization without the full resolver.
- Alternative: `dnsparser` (lighter but less complete). Rejected — missing EDNS0 and DNSSEC support.
- Alternative: Hand-rolled parser. Rejected — DNS wire format has edge cases (name compression, EDNS0, unknown RR types) that are easy to get wrong.

### Chosen: `moka` for DNS cache
- High-performance concurrent cache with TTL support.
- Already commonly used in Rust networking projects.
- Alternative: `DashMap` with manual TTL eviction — simpler but less efficient under high concurrency.

### Evaluated and rejected
- **DNS-over-QUIC (DoQ, RFC 9250)**: Rejected — while more efficient than DoH (no HTTP overhead), it uses a separate port (853) and is a distinct protocol that DPI can identify. DoH over the existing QUIC tunnel is stealthier.
- **DNS-over-TLS (DoT)**: Rejected — uses port 853, identifiable by DPI.
- **dnscrypt**: Rejected — non-standard protocol, limited provider support.
- **OS-level DNS interception (systemd-resolved, NetworkManager)**: Rejected — too platform-specific. iptables REDIRECT is universal on Linux and works regardless of the system resolver.

## Stealth/Efficiency Considerations

### Stealth
- **DoH through tunnel = invisible DNS**: The DNS query is an HTTP/3 POST inside the QUIC tunnel. To an outside observer, it looks like any other VPN data packet. There is no separate DNS protocol, no port 53 traffic, no port 853 traffic.
- **No DNS leak**: All DNS goes through the tunnel. Even if the tunnel drops, the kill switch blocks all traffic including DNS.
- **Wire format, not JSON**: JSON DoH API (`?name=...&type=...`) has a distinctive URL pattern. Wire format POST with `application/dns-message` is less distinguishable from other API calls.
- **Server-side resolution**: DNS queries exit from the server's IP, not the client's. The upstream DNS provider sees the server, not the client.

### Performance
- **DNS cache**: Hot cache hits return in <1ms (local memory lookup). Typical cache hit rate: 60-80% for browsing.
- **Server-side shared cache**: Multiple clients benefit from each other's cache. If client A resolves `google.com`, client B gets a cache hit.
- **Connection reuse**: DoH requests reuse the existing QUIC tunnel connection. No new TLS handshake per DNS query.
- **Negative caching**: NXDOMAIN responses are cached, preventing repeated queries for non-existent domains.
- **Prefetching (future)**: Refresh popular cache entries before TTL expiry to eliminate cold-cache latency.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| iptables REDIRECT requires root/CAP_NET_ADMIN | Coordinate with TODO-441 (privilege dropping): install redirect rule before dropping privileges. |
| DNS proxy adds latency (extra hop through tunnel) | DNS cache with TTL. Typical cached response: <1ms. Uncached: +1 RTT through tunnel. Acceptable trade-off for leak prevention. |
| hickory-proto is a large dependency | Use only `hickory-proto` (wire format), not the full resolver. ~200KB compiled. |
| Large DNS responses (DNSSEC, >512 bytes) | Support EDNS0 UDP payload size negotiation. Fall back to TCP for truncated responses. |
| Server DNS forwarder is a new attack surface | Rate-limit per-client DNS queries. Validate query format strictly. Reject queries to private/internal IP ranges (DNS rebinding protection). |
| Split DNS misconfiguration leaks internal domains | Default: all domains go through tunnel. Split DNS is opt-in. Log a warning when split DNS is enabled. |
| DNSSEC validation adds latency | Off by default. When enabled, cache DNSKEY records (valid for days) to amortize validation cost. |
| macOS/Windows DNS interception differs from Linux | Linux: iptables REDIRECT. macOS: pf rule redirect port 53 to local proxy. Windows: NRPT (Name Resolution Policy Table) or TUN-level DNS interception. Implement platform-specific modules. |
